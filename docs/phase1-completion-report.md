### 8.2 守るルール

- フェーズ2の実装は、持ち主の明示的な開始の指示があってから始める。
- 本番DBの変更は「SQL を作成 → 変更内容と影響を提示 → 持ち主が承認 → 持ち主が SQL Editor で適用」。CI から本番に接続しない。
- 承認済み・適用済みのマイグレーションは編集しない。修正は新しい番号のファイルで行う。
- マイグレーションは1ファイル＝1回の実行。冒頭で `private.schema_migrations` を見て二重適用を止め、前提のバージョンを確認し、末尾で記録する。BEGIN/COMMIT は書かない。
- 次のバージョン番号は `YYYYMMDDNNNNNN` 形式（例: `20261014000001`）。前提として `20261013000001` の適用済みを確認する。
- 全テーブルで RLS を有効にし、ポリシーは `to authenticated` と `private.is_active_member()` を含める。anon には権限を与えない。SECURITY DEFINER 関数は `set search_path = ''`。
- **利用者の所有データの表は、`user_id` を `references public.profiles(id) on delete cascade` にする。** 完全削除はこの連鎖に依存しており、pgTAP（`04_account_deletion`）が `user_id` 列を持つ全表を検査する。企業にぶら下がる表（ステップ・予定など）は `company_id` で企業への cascade にする。
- 管理者でも他人の就活データは見えないようにする（新しい管理者RPCを作る場合も同じ）。
- 日付・時刻は `src/lib/dates.ts` だけを経由する。
- `src/lib/database.types.ts` はマイグレーションに合わせて手で更新する。
- 変更後は lint・typecheck・test・build・check:secrets・`scripts/local-db/run.sh` を通す。
- 有料プラン・独自ドメイン・課金が必要な機能は事前承認。支払い方法は登録しない。

### 8.3 ローカルでの確認方法

```bash
npm ci
npm run lint && npm run typecheck && npm test && npm run build && npm run check:secrets
# DB テスト（ローカルの Postgres 16）
su postgres -c "bash scripts/local-db/run.sh"
```

CI（`.github/workflows/db.yml`）では、同じ pgTAP を素の Postgres と Supabase CLI の両方で動かし、`scripts/supabase-e2e/` の結合テストを認証サービス込みで動かす。新しい表を作ったら `scripts/local-db/supabase-stub.sql` に必要な認証側の表があるかも確認する。
